# Сдача CQA · JSON 1.0

Основание: предоставленный организаторами файл `CQA_Student_Guide_Appendix_Results.pdf`, Freedom Broker, приложение «Как сдать результаты», страницы 1–3. Этот документ описывает требования к формату и их реализацию в CQA Studio.

## Наборы и срок

| Путь от корня Git-репозитория | Содержимое |
|---|---|
| `results/dev/results.json` | DEV: 60 чатов и 5 звонков |
| `results/prod/results.json` | PROD: 10 контрольных чатов |

Контрольный набор выдаётся через 23 часа после старта; стоп-код наступает через 24 часа. Последний час включает получение из API, оценку, проверку, commit и push. Оба файла должны находиться в открытом репозитории, ссылка на который заранее передана организаторам. Локальный файл или один commit этого условия не выполняют. Способ получения контрольного набора сообщают организаторы; его фактическое имя группы может отличаться от `PROD`.

## Структура файла

Файл — один JSON-объект в UTF-8, без комментариев и завершающих запятых.

| Поле | Значение |
|---|---|
| `schema_version` | Строка `"1.0"` |
| `team_name` | Название команды |
| `model.mode` | `"local"`, `"external_api"` или `"hybrid"` |
| `model.name` | Фактически использованная модель; при нескольких — их названия |
| `results` | Одна запись на каждый исходный `conversation_id` набора |

У успешно оценённого диалога есть `conversation_id`, `status: "ok"`, массив `criteria` и объект `score`. Все восемь критериев встречаются ровно один раз.

| Внутренний ID CQA | `criterion_id` | Допустимое `value` | Вес |
|---|---|---|---|
| `c1` | `contact` | `true`, `false` | 10 |
| `c2` | `discovery` | `true`, `false`, `null` | 15 |
| `c3` | `identification` | `true`, `false`, `null` | 20 |
| `c4` | `consultation` | 0, 5, 10, 15, 20, `null` | 20 |
| `c5` | `empathy` | `true`, `false` | 15 |
| `c6` | `dialogue` | 0, 4, 7, 10 | 15 |
| `c7` | `closure` | `true`, `false`, `null` | 5 |
| `c8` | `critical` | `true`, `false` | Отдельный флаг |

В каждом критерии также нужны краткое `rationale` и `evidence_turns` с номерами подтверждающих реплик. Нумерация начинается с 1 в исходном массиве транскрипта. Реплики клиента, бота и системные события тоже занимают позиции. Например, если первые две позиции — клиент и бот, третья — оператор, ссылка на оператора равна `3`, а не `1`.

Внутри CQA Studio доказательства хранятся как ID сообщений. При экспорте они преобразуются в позиции исходного массива. Для отсутствующего действия при отсутствии отдельных цитат экспорт использует сохранённый проверенный диапазон, включая его границы. Диапазон не заменяет наблюдаемые доказательства совершённого действия.

## Итог и ошибка обработки

`score.final_score` — число от 0 до 100, округлённое до двух десятичных знаков. Вклад шкального критерия равен весу, умноженному на оценку и делённому на максимум шкалы. Например, `dialogue: 7` означает 7 из 10 и даёт 10,5 при весе 15 до перераспределения N/A.

При `null` вес соответствующего критерия исключается, а применимые веса пропорционально нормируются до 100. N/A не равно нулю и не является ошибкой обработки. `score.critical_flag` точно совпадает с `critical.value`; значение `true` не обнуляет итог автоматически.

Если оценка не получена, ID сохраняется. Запись имеет `status: "error"`, `criteria: []`, `score: null` и непустое поле `error` с причиной. PROD всё равно должен содержать ровно 10 записей, включая ошибки.

## Как CQA Studio готовит сдачу

1. Импортируйте исходный набор через API или JSON, сохранив `conversation_id` и полный транскрипт.
2. Укажите модель и её фактический режим. Выберите совместимую версию восьми критериев. В списке диалогов можно выбрать все записи по текущему фильтру и запустить пакетную оценку.
3. В «Сдаче результатов» выберите DEV либо PROD и соответствующую импортированную группу. Введите название команды. Просмотрите состав набора, записи с ошибками, предупреждения и JSON.
4. Скачайте `results.json` и разместите его по показанному пути. Проверьте файлы и выполните commit/push до стоп-кода.

Для сдачи CQA Studio использует первоначальные AI-оценки до апелляций. Ручная разметка и пересмотренные оценки доступны в архиве приложения и в сравнении с эталонами. В выбор последнего исхода входят сохранённые неуспешные AI-попытки: более поздний сбой не скрывается более ранним успехом. Повторный успешный запуск становится новым исходом.

Имена моделей берутся из выбранных запусков. Если разные запуски используют разные режимы, общий режим — `hybrid`. В старых запусках режим может отсутствовать: приложение запрашивает явное подтверждение, поскольку текущая настройка не доказывает прежнюю архитектуру. Если сохранённых названий нет и все выбранные исходы — ошибки или отсутствие попытки, можно явно указать фактически использованную модель и режим для файла с ошибками. Требуется подтверждение; эти сведения не выдаются за историю запусков, все записи остаются `status: "error"`. Без сведений о модели официальный экспорт недоступен. Подготовительная ошибка без модели не блокирует другие корректные записи: имя и режим берутся из известных запусков, а отсутствие метаданных у ошибки отмечается предупреждением.

Проверка блокирует несовместимый чек-лист, повторяющиеся или пропущенные ID, неверный состав набора, повреждённые доказательства, расхождение итогов и изменённый транскрипт. Валидная запись с `status: "error"` допускается самим форматом; она видна в диагностике и не получает вымышленный балл.

## Проверка перед push

После `npm ci` можно проверить файл тем же валидатором, который используется в приложении:

```bash
npm run validate:submission -- dev results/dev/results.json
npm run validate:submission -- prod results/prod/results.json
```

Для сопоставления с исходным набором добавьте локальный JSON-ответ API или массив диалогов:

```bash
npm run validate:submission -- prod results/prod/results.json --source /path/to/original-prod.json
```

Без `--source` проверяются формат, количество, уникальность ID и арифметика; совпадение ID с API и границы номеров реплик не подтверждаются. Исходный набор используется только локально, не отправляется по сети и не должен попасть в Git.

Просмотрите изменения и отправьте именно два файла результатов:

```bash
git diff -- results/dev/results.json results/prod/results.json
git add results/dev/results.json results/prod/results.json
git commit -m "Add CQA DEV and PROD results"
git push origin main
```

Откройте оба файла в [erassylls/doomsday](https://github.com/erassylls/doomsday) и убедитесь, что новый коммит доступен. Приложение не подтверждает отправку организаторам: успешное скачивание и проверка JSON отражают готовность формата. Результаты, исходники приложения, опубликованный сайт и Ground Truth — отдельные сущности.

## Состояние подготовленного репозитория

Папки `results/dev` и `results/prod` созданы с `.gitkeep`, чтобы сохранить их до первого экспорта. `results.json` появятся после реальной оценки и действий команды. Тестовые или вымышленные ответы в эти пути не записываются. Проверки реализации используют синтетические данные только в `tests/`.
