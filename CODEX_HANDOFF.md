# Продолжение CQA Studio в Codex

Проект подготовлен для работы из обычной копии исходников: есть `AGENTS.md`, воспроизводимая установка по `package-lock.json` и workflow `.github/workflows/ci.yml`. Для CQA Studio выбран публичный репозиторий [erassylls/doomsday](https://github.com/erassylls/doomsday), основная ветка — `main`.

**Рабочий репозиторий:** `erassylls/doomsday`, ветка `main`. Для продолжения используй актуальную копию из GitHub и проверяй состояние CI для выбранного коммита. Создание среды Codex и публикация Sites — отдельные действия; выполняй их в рамках текущего поручения пользователя.

## Текущее поведение оценки

Пользовательские сценарии и ограничения описаны в [README.md](README.md), правила работы с проектом — в [AGENTS.md](AGENTS.md). При следующих изменениях сохраняй следующие свойства.

### Цитаты, неопределённость и второй проход

[lib/evaluator.ts](lib/evaluator.ts) использует редакцию `EVALUATOR_REVISION = 'cqa-2026-11-07.2'`. В строгой JSON-схеме каждому `criterionId` соответствует собственный набор допустимых значений. Фактические основания и обоснование возвращаются перед выбранной оценкой. Большая схема проверяется до обращения к провайдеру; автоматического перехода в более слабый формат нет.

Внутренний ответ модели содержит `groundedEvidence: { messageId, quote }[]` и `reviewReason: string | null`. Проверяй каждую цитату как непустую точную подстроку исходной реплики с указанным ID. Наружу возвращается прежний `CriterionResult`: `evidence` содержит ID исходных сообщений, а `needsReview` выводится из конкретной причины проверки. Цитата модели не заменяет исходный текст. Для отсутствующего действия сохраняется `checkedRange`; наличие неопределённости само по себе не разрешает N/A.

При `verification: true` второй запрос получает транскрипт и чек-лист без первого ответа и без истории его исправления. При расхождении сохраняется первое допустимое значение, ставится `needsReview`, а предупреждение содержит оба вердикта. Оценки не усредняются. Предупреждения и причины неопределённости обоих проходов сохраняются даже при совпадении значений. На всю операцию разрешён один исправляющий запрос; токены учитываются для всех вызовов. Успешная проверка структуры и цитат не доказывает правильность оценки по существу.

### Метаданные запуска

Новая AI-оценка получает `runConfig` с полями `promptRevision`, `strictJson`, `verification` и `knowledgeHash`. Модель, снимок чек-листа и хеш транскрипта хранятся в существующих полях оценки. Контракт находится в [lib/types.ts](lib/types.ts), запись метаданных — в [lib/server-store.ts](lib/server-store.ts). `runConfig` остаётся необязательным для совместимости со старыми записями; интерфейс учитывает ранние запуски без этих данных.

При изменении инструкций или поведения оценщика обновляй `EVALUATOR_REVISION`. Сохраняй исходные метаданные при апелляциях. `knowledgeHash` различает содержимое базы знаний, но не восстанавливает его; ключи провайдера в снимок запуска не входят.

### Рабочие экспертные эталоны

Раздел «Точность AI» и [lib/calibration.ts](lib/calibration.ts) используют только явно выбранные пользователем оценки с `source: 'manual'`. На один контекст допускается один выбранный эталон. Совпадать должны диалог, сохранённый ID чек-листа, полный снимок критериев и хеш транскрипта. Для эталона берётся один последний совместимый AI-запуск с учётом фильтров модели и редакции оценщика. Причины пропуска неподходящих или неоднозначных записей показываются пользователю.

Сторона AI всегда сравнивается по неизменяемым `initialResults` и `initialScore` до апелляций. Для выбранного ручного эталона используются текущие `results` и `score`. Не подменяй исходный AI исправленными результатами: это исказит метрики модели. Отчёт содержит совпадения по критериям, MAE итогового балла, расхождения N/A и критических флагов, а также экспорт JSON/CSV. При отсутствии сопоставимых данных процент совпадений и MAE равны `null`; пары с ненумерическим итогом не входят в MAE.

Ссылка из сравнения передаёт точный ID запуска и `initialShowOriginal` в карточку диалога. Исходный режим показывает первоначальные балл, обоснования и доказательства; апелляция доступна после перехода к текущему результату. Фильтры модели и редакции, как и выбранные эталоны, хранятся в родительском компоненте и переживают переход в диалог. Регрессии первой отрисовки исходной и текущей версий покрывает `tests/history-view.test.mjs` на полностью синтетических записях.

Эти показатели описывают выбранную рабочую разметку. Они не подтверждают её независимость, не являются заявлением о Ground Truth организаторов и не измеряют качество модели без настоящих AI-запусков. Синтетические тесты проверяют расчёт и контракт. Для содержательных выводов нужна отдельно проверенная разметка.

### Уточнённый шаблон v2

В [lib/rubric.ts](lib/rubric.ts) `CHECKLIST_TEMPLATE_REVISION = 2` обозначает редакцию формулировок встроенного шаблона. Восемь официальных критериев, веса и дискретные шкалы сохранены. Кнопка «Применить шаблон» открывает черновик; сохранение создаёт новый ID и очередную версию чек-листа. Номер сохранённой версии независим от номера редакции шаблона.

Не обновляй ранее сохранённые чек-листы или снимки правил в оценках под видом применения v2. Экспертная разметка и AI должны использовать одну сохранённую версию для сравнения. Уже выполненные оценки и апелляции продолжают опираться на свои исходные правила.

## Приложение организаторов: JSON 1.0

[docs/results-submission.md](docs/results-submission.md) описывает сдачу DEV (60 чатов + 5 звонков) и PROD (10 чатов) в `results/dev/results.json` и `results/prod/results.json`. Раздел «Сдача результатов» и `lib/submission.ts` проверяют весь набор, исходные ID, восемь официальных кодов и типы, веса, шкалы, N/A, номера реплик и итог. Сохраняй полную нумерацию транскрипта с клиентом, ботом и событиями.

Экспорт использует исходные AI-оценки; ручные и пересмотренные результаты не подменяют их. Последний сбой AI должен сохраняться как отдельный `EvaluationFailure` и передаваться с `status: "error"`, пустым `criteria`, `score: null` и причиной. Новый успешный запуск может заменить этот исход в выбранной сдаче, сохранив историю. Не удаляй неоценённые ID из файла. Не заполняй `results/` синтетическими ответами ради формального количества.

Режим `modelMode` сохраняется вместе с запуском, как и фактическое имя модели. Старые записи без режима требуют подтверждения, а не предположения по текущим настройкам. Проверка `npm run validate:submission -- prod results/prod/results.json --source /path/to/original.json` использует общий валидатор и не делает сетевых запросов. Миграция `0001_evaluation_failures` добавляет историю ошибок отдельно от оценок.

## Что связывается между собой

| Компонент | Назначение |
|---|---|
| GitHub | Исходники, история изменений, ветки, PR и результаты CI |
| Codex | Работа с выбранным репозиторием: изменения, проверки, коммиты и PR при наличии доступа |
| Sites | Сборка и публикация выбранной версии приложения, доступ к сайту и его серверные настройки |
| D1 | Данные приложения; локальная база и база опубликованного сайта независимы |

Отправка кода в GitHub не публикует новую версию Sites. В этом проекте не настроен автоматический деплой из GitHub Actions: workflow только устанавливает зависимости, проверяет типы, запускает тесты и собирает приложение. Не рассчитывай на автоматическую синхронизацию изменений, базы или секретов между этими средами.

## 1. Репозиторий и первая загрузка

Целевой репозиторий — [https://github.com/erassylls/doomsday](https://github.com/erassylls/doomsday), ветка `main`. Первая загрузка разрешена пользователем. Перед записью сверяй текущее дерево и ветку, чтобы сохранить изменения, появившиеся после подготовки экспорта. В перенос входят все отслеживаемые файлы приложения: миграции, скрипты, `package.json`, `package-lock.json`, конфигурация сборки, локальные шрифты с лицензией, скриншоты документации, CI, `AGENTS.md` и этот документ.

Сохраняй `.gitignore`, привязку Sites в `.openai/hosting.json` и имена bindings. Не загружай `.dev.vars`, ключи, подписанный адрес источника данных, реальные транскрипты, локальную D1 или runtime-каталоги. Перенос базы не является частью переноса кода. После отправки проверь дерево коммита в `main` и фактический результат CI; не объявляй их успешными по одному лишь наличию локального экспорта.

## 2. Создать среду Codex Cloud

Согласно официальной документации OpenAI, в веб-версии или настольном приложении выбери **Work in → Cloud → Select environment → Create environment**, затем репозиторий `erassylls/doomsday`. Подключи GitHub, если интерфейс запросит это. Codex подготовит зависимости и проверки; после просмотра результатов сохрани настройку среды и выбери **Publish**, затем **Start a new task**. Названия пунктов могут отличаться в другой версии интерфейса. [Официальное руководство Codex Cloud](https://learn.chatgpt.com/docs/cloud).

Для этого проекта при подготовке среды укажи:

- Node.js 24 и npm; минимум проекта — Node.js 22.13.
- Установку `npm ci` из корня репозитория.
- Проверки `npm run typecheck`, `npm test`, `npm run build`.
- Доступ к реестру npm для установки. Доступ к источнику диалогов и выбранному API провайдера потребуется только для настоящих интеграционных запусков.

Опубликовать **среду Codex** означает сохранить рабочее окружение для задач. Это отдельное действие от публикации **приложения Sites**.

`AGENTS.md` содержит правила проекта и автоматически читается Codex при работе в соответствующем каталоге. `CODEX_HANDOFF.md` — обычная документация; в первой задаче явно попроси прочитать её. [Как Codex использует AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

## 3. Запустить локально или в подготовленной среде

Клонируй `erassylls/doomsday` и открой его корневую папку в Codex или терминале. В обычной копии без локального файла профиля сборка автоматически использует переносимый режим и установленный Vinext; управляемый Sites CLI не требуется.

```bash
git clone https://github.com/erassylls/doomsday.git
cd doomsday
npm ci
npm run typecheck
npm test
npm run build
```

Установка и проверки не требуют ключей или реальных транскриптов. Для интерактивного запуска скопируй `.dev.vars.example` в `.dev.vars` и задай переменные отдельно от исходников; команды для Linux/WSL и PowerShell приведены в README. Для настоящей загрузки из API нужен `DATASET_API_URL`. Для AI-оценки выбери доступную модель в интерфейсе и введи ключ в текущей вкладке либо настрой серверный `OPENAI_API_KEY`. При использовании другого провайдера сверяй правила `OPENAI_BASE_URL` и настроек интерфейса с README и серверным кодом. Доступ к Codex сам по себе не настраивает провайдера оценки в приложении.

```bash
npm run setup:local
npm run dev
```

`setup:local` при необходимости собирает Worker и применяет миграции из `drizzle/` к локальной D1. Открой адрес, напечатанный сервером. После изменений схемы добавляй новую миграцию и повторяй подготовку локальной базы; не переписывай уже применённые миграции как способ обновления существующих данных.

Текущий backend допускает только публичный HTTPS-адрес AI-провайдера. `localhost`, HTTP и внутренние адреса отклоняются даже при локальном запуске приложения. Не обещай подключение локальной LLM без доступного приложению разрешённого HTTPS-endpoint и отдельной проверки интеграции.

Ключи и адреса источников для опубликованного сайта задаются отдельно в его серверных настройках. GitHub Actions не нуждается в них: тесты используют синтетические данные и подставленные ответы провайдера.

## 4. Рабочий цикл

1. Начни задачу с актуальной целевой ветки и прочитай `AGENTS.md`.
2. Внеси конкретное изменение в отдельной ветке. Проверь формулу, доказательства, версионирование или апелляции, если задача затрагивает их.
3. Выполни `npm run typecheck`, `npm test`, `npm run build`; для интерфейса проверь сценарий в браузере. Просмотри diff и `git diff --check`.
4. Для согласованных изменений сохрани коммит, отправь рабочую ветку в `erassylls/doomsday` и открой PR в рамках поручения пользователя. Первая загрузка в `main` уже разрешена. После запуска GitHub Actions проверь фактический результат workflow; локальная сборка не доказывает успешность удалённого CI.
5. В рамках поручения на публикацию отдельно обнови исходники проекта Sites и опубликуй проверенную версию. Убедись, что новая публикация завершилась успешно, затем проверь сайт.

Для первой задачи можно использовать такой текст:

```text
Прочитай AGENTS.md, README.md и CODEX_HANDOFF.md в erassylls/doomsday (CQA Studio).
Проверь текущую ветку и незавершённые изменения. Установи зависимости по lockfile,
выполни typecheck, тесты и сборку. Продолжай разработку по моей следующей конкретной
задаче, сохраняя реальный AI-режим, формулу N/A, точные доказательства, снимки запусков
и историю апелляций. В сравнении с выбранными экспертными эталонами используй
исходные AI-результаты до апелляций. Сообщай фактический результат проверок.
Первая загрузка исходников в erassylls/doomsday уже разрешена. Следующие commit/push,
PR и публикацию выполняй в рамках текущего поручения. Не считай push в GitHub
публикацией приложения Sites и не объявляй CI успешным без результата workflow.
```

## Что требуется после подготовки кода

- Продолжать работу в `erassylls/doomsday`, сохраняя актуальные изменения в `main`. Первая загрузка выполнена; проверять каждый новый CI-запуск отдельно.
- Разрешить этому репозиторию доступ в подключении GitHub, если он не виден в Codex, и создать или выбрать среду Codex.
- Проверять CI на GitHub для нового коммита; первая загруженная версия прошла workflow.
- Для настоящего AI-прогона настроить модель, ключ и источник диалогов в той среде, где будет работать приложение.
- Получить Ground Truth для отдельной проверки качества. Успешные unit-тесты и сборка не дают оценки точности на скрытых диалогах.

В текущей разработке можно подготовить рабочие экспертные эталоны и использовать раздел «Точность AI» для внутреннего сравнения. Он не заменяет отдельную проверку по Ground Truth организаторов и не требует переноса проекта в GitHub.

Рекомендации по интерфейсу Codex сверены с официальной документацией OpenAI 7 ноября 2026 года. Команды проекта следует сверять с текущим `package.json` после дальнейших изменений.
